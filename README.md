## 문제

업횟(업그레이드 가능 횟수)이 유일한 희소 자원이다. 성공·실패 무관하게 1씩 줄고,
아이템 파괴는 없다. 슬롯당 기대 공격력은 60%가 1.2로 가장 높다.

| 주문서 | 성공률 | 공격력 | 슬롯당 기대치 |
| ------ | ------ | ------ | ------------- |
| 100%   | 1.0    | +1     | 1.0           |
| 60%    | 0.6    | +2     | 1.2           |
| 10%    | 0.1    | +5     | 0.5           |

그럼에도 10%를 쓰는 이유는 **분산**이다. 업횟 7회를 60%로만 채우면 기댓값은 공8.4,
최대는 공14다. 목표가 평균보다 위에 있으면 분산을 사야만 도달 확률이 생긴다.
여기에 "실패한 무기를 팔고 새로 시작한다"는 선택지가 붙어 재시작 옵션이 있는
확률적 동적계획 문제가 된다.

## 엔진 구조 (`src/lib/enhance`)

상태는 `(남은 업횟 u, 정옵 대비 공격력 a)` 하나뿐이라 격자가 작고, 전체 해가 수 ms에 나온다.

| 파일            | 역할                                                      |
| --------------- | --------------------------------------------------------- |
| `dp-cost.ts`    | 모드 A — 목표 달성 최소 기대비용과 최적 정책              |
| `dp-budget.ts`  | 모드 C — 예산 제약 하 달성 확률 최대화                    |
| `evaluate.ts`   | 정책 고정 후 비용 CDF·분위수, 아이템 1개의 결과 분포      |
| `breakeven.ts`  | 주문서별 손익분기 가격 역산                               |
| `salvage.ts`    | 시세 보간과 상태의 **이론가** 유도                        |

### 재시작 고정점

손절 후 재시작하는 비용에 시작 상태의 값 `R` 이 다시 등장한다. `R` 을 고정하면 나머지는
업횟 오름차순 한 번의 스윕으로 끝나므로, 바깥에서 `R` 만 맞추면 된다. `f(R)` 은 비감소이고
기울기가 1 이하라 `R=0` 에서 `R ← f(R)` 을 반복하면 **최소** 고정점으로 단조 수렴한다
(Aitken Δ² 가속, 오버슈트 시 폐기).

### 남은 업횟의 가치는 묻지 않고 유도한다

사용자에게 받는 시세는 **업횟 0회 기준 공격력별 시세** 하나뿐이다. 업횟이 남은 상태의
값은 엔진이 계산한다.

```
W(0, a) = V(a)                          업횟을 다 쓴 것만 팔린다
W(u, a) = max_s [ E W(u−1, ·) − c_s ]   업횟이 남으면 못 파니 계속 발라야 한다
```

업횟이 남은 매물은 실제로 거래가 거의 없다(10% 초벌처럼 그 자체로 값이 붙는 경우는 예외).
그래서 중간에 손절하려면 남은 업횟을 다 태워 완작으로 만들어야 판다고 본다. 그 결과
**남은 업횟이 부채가 될 수도 있다** — 주문서값이 올려 주는 값어치보다 비싸면 `W(u,a)` 가
`V(a)` 보다 낮게 나온다.

완작 시세를 하나도 안 채우면 **되팔기가 꺼진다** (손절 회수 0). 리버스처럼 장착하면
교환불가가 되어 되팔 수 없는 아이템이 이 경우다.

곡선의 **양 끝 바깥으로는 외삽하지 않고 끝점 값을 그대로 유지한다.** 위로 연장하지 않는
이유는 폭주다 — 공격력당 2배씩 뛰는 곡선은 몇 단계만 늘려도 값이 터진다. 아래로 연장하지
않는 이유는 시장이 먼저 사라지기 때문이다. 어느 선 밑으로는 완작이라도 유저끼리 거래가 안
되고 상점 판매가가 회수의 전부인데, 상점가는 공격력을 따라 내려가지 않는다. 곡선을 늘려
0 근처로 떨어뜨리는 것보다 **채운 칸 중 최저 공격력의 값을 바닥으로 까는 쪽**이 현실에
가깝다. 그래서 그 최저 칸은 **상점 판매가**를 적는 자리이고, 상점에 팔 생각이 없으면 **0**
을 적는다. 화면의 완작 시세 표는 값을 적어 둔 하옵 매물이 있으면 그만큼 아래 칸까지
열린다 — 그래야 "하옵 완작은 상점행" 을 적을 수 있다.

"1회당 N메소" 같은 상수를 입력받으면 시세 곡선과 거의 반드시 모순이 난다. 예컨대 공7이
600만, 공8이 900만인데 100% 주문서가 30만이라면, 1회 남은 공7은 그 자체로 870만 이상의
가치가 있다. 회당 10만이라고 적으면 사서 주문서 한 장 바르는 것만으로 260만이 공짜로 생기는
차익거래가 모델 안에 생겨 최소비용이 −∞로 발산한다. `W` 는 정의상 그 구멍이 없고, 덤으로
**매물 가치 평가**("이 공5 3회 남은 것 적정가?")에 그대로 쓰인다.

### 리버스 무기 — 시작 공격력이 랜덤인 경우

리버스 무기는 아이템 레벨이 오를 때마다 공격력·주스탯·부스탯이 확률적으로 오른다
(기본값은 3회, 회당 공 +0/30% · +1/50% · +2/20%). 확률은 유출된 값이 아니라 유저들의
추정이라 화면에서 직접 조절할 수 있다.

모델은 **레벨업을 먼저 끝낸 뒤 강화를 시작한다**고 본다. 레벨업은 메소가 아니라 사냥
시간을 쓰므로 이 모델에서 공짜이고, 시작 공격력을 보고 주문서 전략을 짜면 나쁘게 뜬
무기에 주문서를 붓는 일을 피할 수 있다. 정보가 늘 뿐이라 손해 볼 여지가 없다. 실제로
어느 쪽을 먼저 하느냐는 취향에 가깝고(사냥할 때 이미 강화된 무기를 들고 싶다든가),
여기서 다루는 건 메소 기준의 최적이다.

엔진에는 `Problem.startBonus` 하나로 들어간다 — 격자에 들어서는 지점이 한 칸이 아니라
분포가 되고, 손절 후 새로 사는 무기도 다시 굴린다. 강화 분석에 반영되는 건 공격력뿐이고
주스탯·부스탯은 분포만 보여 준다. 상태를 공격력 하나로 잡고 있어서 스탯까지 넣으면
격자가 통째로 커진다.

### 예산이 정해지면 사야 할 매물이 달라진다

돈에 제한이 없으면 답은 **기대비용이 가장 싼 매물**이다. 실패해도 다시 사면 되니
싸게 여러 번 도전하는 쪽이 대개 이긴다. 예산이 정해지면 이야기가 달라진다 — 재도전할
돈이 없으면 시작 공격력을 돈 주고 사야 하고, 반대로 너무 비싼 매물을 사면 정작 바를
주문서를 못 산다. 그래서 **가진 돈이 얼마냐에 따라 사야 할 물건이 바뀐다.**

기준 문제(목표 +7, 업횟 7)에서 손으로 확인되는 경계가 그 예다.

| 가진 돈 | 사야 할 매물 | 달성 확률 | 왜 |
| --- | --- | --- | --- |
| 420만 | 공1하 (200만) | 60% | 60% 한 장 + 100% 여섯 장 = −1+2+6 = +7, 한 번의 승부 |
| 540만 | 정옵 (400만) | 100% | 100% 일곱 장이면 확률 없이 +7 이 확정된다 |

최소비용 기준으로는 여전히 공1하가 답이다. 확정을 사려면 더 비싼 매물이 필요하다는
것, 그게 예산 곡선(초록)이 비용 곡선(파랑) 위로 벌어지는 이유의 절반이다.

예산 DP 는 원래 예산 틱마다 모든 매물을 비교하고 있었으므로(그래서 초록 곡선이 그렇게
그려진다) 답은 이미 격자 안에 있었다. 그걸 `startBase[b]` 로 남기고 구간으로 접어
(`startBands`) **결론 패널**에 올린 것이다 — "무엇을 사라"는 예보가 아니라 지금 할
일이라, 곡선 옆이 아니라 결론에 있어야 한다. 두 가지를 조심해야 한다.

- **사용자의 예산 지점에서 읽어야 한다.** 곡선을 그리려고 예산 DP 는 사용자가 적은
  금액보다 넓은 구간까지 푼다. 끝점에서 첫 매물을 읽으면 있지도 않은 돈을 가진 사람의
  답이 나온다.
- **틱마다 argmax 를 그대로 쓰면 답이 널뛴다.** 매물별 확률은 서로 바짝 붙어 있고
  ("한 번 더 도전할 수 있느냐"가 예산에 따라 오락가락한다) 격자 잡음도 0.1%p 쯤 얹힌다.
  그래서 예산 오름차순으로 훑으며 **쥐고 있던 매물이 1%p 넘게 뒤처질 때만** 갈아탄다
  (`SWITCH_MARGIN`). 대가는 명확하다 — 표가 권하는 매물은 그 예산의 최선보다 최대 1%p
  못하다. 그 대신 답이 몇 개의 구간으로 뭉쳐 "얼마부터는 이걸 사라"를 말할 수 있다.

매물들이 사실상 비긴 문제에서는 구간이 하나로 접힌다. 그럴 땐 "예산과 무관하게 이걸
사라"고 말하는 게 맞고, 실제로 예제 시나리오가 그 경우다.

### 이 도구가 의미 있는 조건

시세가 완전히 정합한 시장에서는 답이 자명해진다 — 목표 완성품을 살 수 있다면 최소비용은
정확히 그 시세다. 이 분석이 실제로 값을 하는 상황은 둘이다.

1. **목표 완성품 매물이 없다.** 공10짜리를 파는 사람이 없으니 직접 만들어야 한다.
   (목표 공격력의 시세를 비워 두면 이 모드가 된다.)
2. **매물이 이론가보다 싸다.** 엔진이 이걸 찾아내면 그 사실을 먼저 알린다.

## 알려진 근사

- **예산 축은 음수 지출을 표현하지 못한다.** 공6을 팔면 새 하옵을 사고도 돈이 남는 경우가
  있는데, 예산 모드와 비용 CDF는 그 초과분을 재투자하지 못하는 것으로 본다(`creditCapped`).
  결과는 보수적인 쪽으로 치우친다. 헤드라인인 기대 순비용은 이 근사를 쓰지 않는 엄밀값이다.
- 비용을 예산 격자에 올릴 때는 **확률적 반올림**을 써서 이산화 편향을 없앴다.
  매번 올림/내림하면 수십 번의 행동을 거치며 편향이 누적돼 분포가 통째로 밀린다.

## 화면 (`src/components`)

| 파일 | 역할 |
| --- | --- |
| `Analyzer.tsx` | 입력 상태와 결과 조립 |
| `InputPanel.tsx` | 시세·목표 입력 |
| `PolicyHeatmap.tsx` | (남은 업횟 × 공격력) 격자에 최적 행동을 칠한 시그니처 화면 |
| `charts.tsx` | 누적 확률 곡선, 가로 막대 |
| `StateAdvisor.tsx` | 지금 들고 있는 아이템의 "계속 vs 손절" 판정과 목표 달성 확률 |
| `BudgetStartPlan.tsx` | 결론에 붙는 "네 예산에서는" 한 줄과 예산 구간별 첫 매물 표 |
| `storage.ts` | 입력값을 브라우저에 남기고 되읽기 |

입력한 값은 **이 브라우저에만** 남는다 (localStorage 키 `ml:enhance:state`). 서버가
없으니 어디로도 보내지 않고, 입력 패널 맨 아래 **입력 초기화**로 지운다. 시세를 스무 칸
채워 놓고 새로고침 한 번에 잃으면 두 번째 방문부터 쓸 이유가 없어서 넣었다.

같은 오리진에 다른 유틸들이 함께 올라가 있어 키에 `ml:enhance:` 접두어가 붙는다. 읽을
때는 칸마다 검사해서 이상한 칸만 기본값으로 되돌린다 — 예전 판이 쓴 값이나 손으로 고친
값이 그대로 격자에 흘러 들어가면 화면이 통째로 죽는다.

계열색 4종(주문서 3 + 손절)은 dataviz 검증기의 all-pairs 기준을 통과한 조합이다
(dark, surface `#1a1d21`). 색맹 분리 ΔE 7.2 로 경고대에 있어 **보조 인코딩이 필수**이며,
그래서 격자의 모든 칸에 문자 라벨이 함께 들어간다. 색을 바꾸려면 검증기를 다시 돌릴 것.

## CI

검증 단계는 `.github/workflows/checks.yml` 한 곳에만 있고, PR 과 배포가 이를 재사용한다
(`workflow_call`). 배포 워크플로는 여기에 Pages 하위 경로를 넘기고 결과물을 아티팩트로
받아 그대로 올린다 — PR 에서 통과한 것과 같은 빌드가 배포된다.

놓으면 이질감이 커서, 이용자가 주문서를 헷갈리지 않는 쪽을 택했습니다. 넥슨의 허락을
받은 것은 아니며, 요청이 있으면 삭제합니다. 포크하시는 분은 이 파일들에 대해 독자적으로
판단하시기 바랍니다.

받아오는 방법은 `scripts/fetch-game-icons.mjs` 에 남겨 두었습니다 — 어떤 파일이 어디서
왔는지가 코드로 드러나야 경계가 흐려지지 않습니다.

**Galmuri** 글꼴은 [SIL Open Font License 1.1](https://github.com/quiple/galmuri) 이며,
이 저장소는 글꼴 파일을 포함하지 않고 CDN 에서 불러옵니다.

MapleStory / 메이플랜드는 넥슨의 저작물이며 이 프로젝트는 넥슨과 무관합니다.
